The governed AI development lifecycle

From clear intent to proven code, with any model.

Masscode is an open source AI development lifecycle. It turns what you want to build into clear requirements and decisions, then has coding agents deliver the work under rules a program can check.

The value

Most of what software costs is decided before the first line of code. Masscode puts its effort there, then proves the code kept those promises.

Five pillars

What sets Masscode apart.

01Decision support

Clear requirements from the first conversation.

Masscode starts with why the project exists, then the features that serve it, then requirements with measures and non goals. Decisions come one at a time, each briefed by an advisor that researches current sources and draws the diagram you need.

  • Each brief shows only the facts that decision touches, with two or three options and what each one opens and closes.
  • Routine decisions are accepted in a batch, so your attention goes where it matters.
  • A decision reopens by itself when a measurement crosses one of its assumptions.
In the cockpitD-05 reopened when the graph grew past its recorded limit.
02Rule enforced decision graph

A project graph that enforces its own rules.

Objectives, requirements, decisions, constraints, tasks and tests are typed facts in one graph built on open standards. Rules check the graph when work is defined and again when code lands, so what was agreed stays agreed.

  • Every accepted decision emits a constraint that a program checks.
  • A rule that rests on an unapproved term answers unknown, and unknown never counts as a pass.
  • Every gate is a signed commit in your repository, with readable decision records and an evidence bundle for each merge.

03The failure mode

When something goes wrong, it stops and tells you why.

Each task runs in a sealed sandbox that may only write to its own folders. A separate agent writes the tests, programs run the checks, and a reviewer reads the change before you approve it.

  • Anything unusual parks the task with the reason and your options. It never guesses its way forward.
  • Repair rounds and budgets are capped by risk tier, and a test that did not run is never a pass.
  • Every failure is logged and becomes a lesson for the next run.
In the cockpitWave 2 of 3: seven tasks merged, one parked for a person.
04Open and sovereign

Any model, any environment, nothing locked in.

The engine is open source and runs on one machine under Docker, in your private cloud or fully offline, so regulated data stays in the jurisdiction you choose. Pick a model for each role: Claude, OpenAI, GitHub Copilot, or a local model through LM Studio, Ollama or vLLM.

  • A role you keep local never falls back to the cloud. It waits instead.
  • Secrets go to a broker, and no agent or model ever sees them.
  • Works with GitHub, Linear and Jira, and exposes its contracts through OpenAPI and MCP.
In the cockpitLocal models write and test code. Hosted models are an explicit choice.
05Token and cost reduction

Fewer tokens, predictable spend.

Agents get small, fenced tasks with only the context they need: a map of the code instead of the whole repository, and a slice of the graph instead of the whole project. Programs settle what they can, so models are asked only about the rest.

  • Routine work runs on local models, and paid models are kept for the reviews that need them.
  • Every call is priced and attributed to a project, a task and a cause, rework included.
  • At a project's cost cap, new tasks wait until you raise it.
In the cockpitRework is shown in its own colour, so waste is visible at a glance.
How it runs

Six stages, each ending at a gate you approve.

  1. 01

    Onboard

    A few questions set the project type, review level, models and cost limits.

  2. 02

    Define

    Objectives, then features, then requirements with measures.

  3. 03

    Decide

    Architecture, data, security, testing and design.

  4. 04

    Break down

    Tasks grouped into waves by a solver.

  5. 05

    Deliver

    Implementation, tests, checks and review for each task.

  6. 06

    Prove

    Each merge carries its evidence into the graph.
